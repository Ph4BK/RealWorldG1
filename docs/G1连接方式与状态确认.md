## 7. 路线决策与推荐部署方式

当前选择 Python 路线：在上述兼容容器中基于 `rclpy + unitree_api` 实现
`G1MotionExecutor`，参照已经构建验证的 C++ `LocoClient` 请求/响应协议。
当前不依赖缺少 G1 子模块的 `unitree_sdk2py 1.0.1`，也暂不增加 C++ 常驻适配进程。

推荐将 G1 专用轻量化代码部署到 PC2 的独立容器，并由容器内 ROS 2/CycloneDDS
直接与 PC1 通信：

```text
开发机或实验室服务器
  ├─ SSH/SCP：代码部署、进程管理、日志查看
  └─ 可选：低频目标、文本任务或重型模型推理结果
                         │
                         ▼
G1 PC2（192.168.123.164）
  └─ UniGoal G1 容器
      ├─ UniGoal G1 轻量化程序
      ├─ 感知、地图、局部规划和安全检查
      ├─ Python G1MotionExecutor（rclpy + unitree_api）
      └─ ROS 2 Humble / CycloneDDS
                         │ G1 内部 DDS
                         ▼
G1 PC1（192.168.123.161）
  └─ 运动控制
```

在该架构下：

- PC2 到 PC1 的运动控制不需要经过 rosbridge。
- SSH 仅用于部署与管理，不是运行时运动控制通道。
- 如果重型感知或大模型仍运行在实验室服务器，可保留 rosbridge 或其他网络接口传输低频高层信息。
- 高频运动控制、安全检查与失联处理应留在 PC2/PC1 本地，不应依赖 Wi-Fi 实时闭环。
- 第一阶段客户端只允许调用 7001–7005 等查询接口，不实现或暴露运动接口。
- 查询接口及请求/响应匹配确认后，再依次加入受保护的 `StopMove` 和 `SetVelocity`。

## 8. G1 只读并发客户端实现与真机验证

已在 `RealWorldG1/src/` 实现第一版 Python 客户端：

- `g1_api_client.py`：与 ROS 2 解耦的并发请求核心及只读接口。
- `ros2_sport_transport.py`：`rclpy + unitree_api` DDS 传输层。
- `check_g1_loco_service.py`：7001–7005 五项只读检查器。
- `run_g1_loco_check.sh`：在 PC2 上用已验证镜像运行检查器。

客户端使用一个持久的 `/api/sport/response` 订阅者，并以
`pending_requests[request_id]` 匹配并发请求。请求 ID 使用带单调递增保护的
`time.monotonic_ns()`。默认最多同时等待 4 个请求，默认单项超时 5 秒。请求会在发布前
先登记到字典；响应可乱序到达。未知、重复或超时后的迟到响应会被忽略；API ID 不一致、
非零服务端状态、畸形 JSON、超时和关闭均通过明确异常结束对应 Future。

公共客户端当前只提供 7001–7005 的具名查询方法，源码中没有通用的公共
`call(api_id)`，也没有 7101–7107 控制方法，以避免绕过安全边界。

本地无 ROS 环境的单元测试共 11 项，已经全部通过，覆盖：

- 发布前登记、乱序响应及同 API 并发；
- 未知、重复和迟到响应；
- API ID 错配、服务端错误及畸形 JSON；
- 超时清理、并发上限、关闭取消及多线程同步调用。

### 8.1 PC2 运行方式

将仓库部署到 PC2 后，在仓库根目录执行：

```bash
bash RealWorldG1/tools/run_g1_loco_check.sh --timeout 5 --max-pending 4
```

脚本使用 host network，并在加载 `/root/unitree_ros2/setup.sh` **之后**设置
CycloneDDS 使用 `eth0`。初始化顺序不能颠倒，因为该 setup 脚本会把已有的
`CYCLONEDDS_URI` 覆盖为不适用于当前 PC2 的 `enp3s0`。传输层还会等到 request
reader 和 response writer 都被 DDS 发现后才允许发布第一条请求，避免启动后立即发布
造成首包丢失。

### 8.3 遥控切换走跑模式后的对照结果

现场通过遥控器将 G1 从开机播报的“零力矩模式”切换到走跑模式后，使用完全相同的
只读检查器再次测试：

| 查询 | 零力矩模式 | 遥控走跑模式 |
|---|---:|---:|
| FSM ID（7001） | `0` | `802` |
| FSM mode（7002） | `0` | `0` |
| Balance mode（7003） | `7301` | `7301` |
| Swing height（7004） | `7301` | `7301` |
| Stand height（7005） | `7301` | `7301` |

FSM ID 从 `0` 变为 `802`，证明遥控模式切换已经被 sport 服务观察到，也再次验证了
查询链路能够读取实时状态。现场进一步实测，在 FSM 802 下遥控器可以控制 G1 前后、
左右、旋转并执行内置动作。因此可以把本机的 `802` 操作性地确认为“厂商内部控制器的
遥控走跑/动作模式”。公开的 Unitree SDK 没有给出 `802` 的正式符号名，所以本文不把它
写成一个已经由官方头文件定义的通用枚举。

但是 `7301` 在走跑模式下仍然存在，因此不能再把 `LocoState not available` 单独归因于
零力矩模式。本机还确认 `/sportmodestate` 端点声明类型为
`unitree_hg/msg/SportModeState`，而当前容器的 Unitree ROS 2 0.3.0 中
`unitree_hg.msg` 不包含 `SportModeState`；该容器只在 `unitree_go.msg` 中提供同名类型。
这构成了客户端消息定义与当前 G1 固件接口不匹配的直接证据，并使现有容器无法反序列化
该 G1 状态话题。

在确认控制权、固件/API 兼容性及 FSM 802 的含义之前，不能用 7003–7005 的失败来
判断机器人没有进入走跑模式，也不能据此假定 7105 `SetVelocity` 一定可执行。
特别是，遥控器能驱动机器人只证明厂商内部控制器拥有有效控制通路，并不证明外部 SDK
客户端已经取得相同的运动控制权。

CheckMode 的查询格式来自
[官方 MotionSwitcherClient](https://github.com/unitreerobotics/unitree_sdk2_python/blob/master/unitree_sdk2py/comm/motion_switcher/motion_switcher_client.py)。

sport API 版本与公开 G1 Loco API 的 `1.0.0.0` 相同，但相同版本字符串不能保证
所有固件的 FSM、查询能力和控制前置条件一致。缺少 `unitree_hg/SportModeState`
只能解释本地无法解析该状态话题，不能直接解释服务端返回 `7301`：这些查询的请求与
响应使用的是已验证可工作的 `unitree_api` 消息。`7301` 的具体服务端触发条件仍未查明。

还需修正控制权接口的理解：[官方用户控制示例](https://github.com/unitreerobotics/unitree_sdk2/blob/main/example/g1/high_level/g1_userctrl_dds_example.cpp)
在 PASSIVE 状态下，以 `SwitchToUserCtrl()` 配合 `rt/user_lowcmd` 发布关节位置、增益和
力矩命令，再用 `SwitchToInternalCtrl()` 返回内部控制。因此不能将这组接口当作
高层 `SetVelocity` 的通用授权开关，也不能将 `ReleaseMode()` 当作速度控制的准备步骤。
本次没有调用这些接口。

PC2 固件线索：

- `/etc/user_release_version` 为占位标记 `User release: 0.0`。
- `/unitree/robot/pkg/version/version.json` 的 `Package` 为空，仅列出 PC4 模块版本，
  不能作为 PC1 或整机固件版本。
- OTA 日志包含 `package_1.5.1.1_G1_Edu+_upk` 中 PC4 补丁的传输、校验及解包记录。
  这些历史记录不能证明当前整机运行 1.5.1.1，也不能推断当前为其他设备案例中的 1.5.3。

后续需要从官方 App 的设备版本页面或厂商认可的整机版本查询取得当前固件版本，
再确认该版本 FSM 802 对高层速度接口的支持与前置条件。

## 9. 尚未完成的验证

以下项目尚不能由当前结果确认：

- WSL 是否能直接发现 G1 的 DDS/ROS 2 话题；SSH 成功不等于 DDS 组播成功。
- `/dog_odom` 的实际位移/转角尺度、短期重复性和长期累计漂移。
- 激光雷达、相机、里程计之间的时间同步和外参。
- PC2 的具体 Tegra/Jetson 模块型号、GPU 算力、CUDA/JetPack 版本及可用于模型的共享显存。
- FSM ID `802` 的固件侧含义，以及为何走跑模式下 7003–7005 仍无 LocoState。
- G1 balance mode、运动接口调用前置条件、停止延迟及安全停机流程。
- 实验室路由器重启后，开发机地址是否变化，以及 PC1/PC2 地址是否为静态配置。

后续仍应优先执行只读检查。在建立吊装、急停和现场监护条件之前，不要向 `/api/sport/request`、`/lowcmd`、`/user_lowcmd` 等控制话题手动发布消息。
